01
AI 应用分层

Model 推理；Tools 声明并实现能力；Harness 编排运行时；Context 为输入集合；Agent 为面向目标的多步自主循环。

层级职责
Model基于 Context 推理；生成文本或结构化 tool_calls
Context单次请求提供给模型的全部输入
Toolsschema 声明 + 可执行实现
Harness循环、执行、回写、权限、资源、Context 组装
Agent目标驱动的多步循环，直至完成或强制终止
  • 模型不直接执行外部副作用；由 Harness 调度 Tools 完成。
  • 与带工具的单轮对话的差异：是否具备目标驱动的多步循环。
02
Context Engineering

决定窗口内放入哪些信息、顺序与篇幅，并使组合适配当前任务。

Prompt EngineeringContext Engineering
关注点指令如何编写装载内容、容量分配、压缩与检索
关系产出是 Context 的组成部分统筹整窗信息
  • 参考优先级：当前用户请求 → 系统说明/已激活规范 → 工具 schema → 当前步骤证据 → 历史（可摘要）→ 大文件全文（应切片/摘要）。
  • 优先级随任务动态调整；工作集片段与刚返回的工具结果可高于无关历史。
03
Context 组装策略

在窗口容量受限时，通过切片、摘要、检索与按需记忆管理 Context 预算。

策略定义适用
工作集切片从已确定对象选取相关片段目标已知
摘要压缩压缩历史/长文后写回后续 Context需保留要点、释放容量
RAG索引/相似度检索后写入 top-k语料大、位置未知
长期 Memory窗外持久化，按需检索注入跨会话信息；禁止每轮全量注入
  • 摘要压缩服务于 Context 预算，不同于向用户交付总结的产品功能。
04
Prompt Engineering 与 Function Calling

设计模型侧指令、示例与输出约束，以及工具调用意图的生成方式；执行仍由应用侧完成。

4.1 消息角色
  • system / user / assistant / tool：系统约束、用户输入、模型输出、工具结果回传。
4.2 System Prompt 要素
要素说明
角色身份与能力边界
任务目标
约束禁止项与规则
输出格式结构与呈现
  • 抽象规则的遵循弱于对具体示例的模仿；关键格式应辅以示例或 API 级约束。
4.3 Zero-shot / Few-shot
  • Zero-shot：无示例直接下达任务。
  • Few-shot：先给输入→输出示例；用于固定模式与边界情形覆盖。
4.4 Chain of Thought
  • 自回归生成若不展开中间步骤易跳步；强制中间推理可降低错误率。
  • Zero-shot CoT：引导分步思考，适用于通用推理。
  • Few-shot CoT：示例展示完整推理链，适用于领域特定推理方式。
4.5 结构化输出
  • 可靠性递进：Prompt 描述格式 → Few-shot 示范 → API response_format / constrained decoding。
  • 严格 schema 应优先采用 API 级约束。
4.6 Prompt 调试
  • 定位失败样例 → 最小修改 → 回归测试（含未改动相关用例）。
4.7 Function Calling
  • 模型输出结构化 tool_calls；应用侧执行并将结果以 tool 消息写回。
  • Schema 应说明：能力、适用场景、限制与参数约束。
  • 单轮通常含两次模型请求；多轮需步数上限与重复检测。
  • 一般错误可脱敏回传模型；安全相关错误由代码层兜底。
  • 意图选择倾向由模型完成；状态机、权限与安全校验由代码完成。
05
Harness Engineering

包裹模型的运行时：保障循环可运行、可终止、可审计，并落实安全与资源策略。

应由 Harness 强制可由 Prompt 表达
循环与步数上限；工具执行/超时/重试；高危确认；配额；Context 与 Memory 管线；日志语言、语气、详尽程度等偏好
  • 不可逆损害、资源失控、循环无法收敛：必须由代码强制。
06
Agent Loop

感知 → 规划 → 行动 → 观察，可迭代执行。

阶段职责
感知模型判断缺口；Harness 调度采集；结果回写后再解释
规划模型拆解步骤
行动模型发出 tool_calls；Harness 调度；Tools 产生副作用
观察结果写回 Context；模型评估是否达成目标
  • 终止：模型判定完成，或 Harness 触发最大步数/超时/用户取消。
07
工具调用协议位置

执行依据为结构化 tool_calls，而非自然语言思考文本。

  • 流程：tool_calls → Harness 调度 Tool → 结果写入 Context → 再次请求模型。
  • 仅有自然语言意图、无 tool_calls 时，不得执行外部操作。
08
SKILL

任务向流程规范（SOP）；由 Harness 发现并注入 Context；通常不是可 call 的业务工具。

  • 渐进披露：目录元数据常驻；全文按需加载。
  • 触发：用户显式指定、Harness 匹配、模型依据目录选择后加载。
  • 注入后模型按规范调用普通 Tools 或继续推理。
09
MCP 能力模型

Host 与外部能力进程之间的标准协议；模型不直连 Server。

能力定义
Tools可调用动作 + schema；Server 执行
Resources可读取数据/文档，作为 Context 原料
Prompts可参数化提示模板
  • 拓扑：用户 → Host（含 Client）↔ Model；Client → Server → 外部系统。
10
MCP 传输与生命周期

本地常见 stdio（子进程 + JSON-RPC）；远程多采用 Streamable HTTP 等。

  • Spawn：Host 启动 Server 并建立 Client。
  • Initialize：握手，协商版本与能力。
  • List：枚举能力声明并纳入 Context。
  • Call：Client 发起调用，Server 执行并返回。
  • stdio 下 stdout 专用于协议；日志写入 stderr。
  • 参考实现：notes/mcp-demo/。

SKILL 与 MCP

SKILL 规定如何完成任务；MCP Tool 提供接触外部系统的可执行能力；二者可组合。

12
权限、沙箱与安全边界

硬约束位于 Harness 与凭证设计；Prompt 安全说明为软约束。

风险控制面
高危本地操作Harness：拦截、确认、沙箱
凭证权限过大最小权限 scope；敏感操作可再审批
敏感信息外泄禁读/脱敏/拦外发；凭证不写入模型 Context
能力授予过宽工具白名单与沙箱，最小能力集
13
端到端结构

编码助手类任务的参考流水线：组窗 → 决策与工具循环 → 外部变更（如 PR）→ 强制安全与终止策略。

  • Harness 组装 Context（系统说明、项目约束、工具/MCP schema、SKILL 目录或全文、代码与日志片段）。
  • 模型规划并产生 tool_calls；Harness 执行回写；循环至完成或强制终止。
  • 经 MCP 或平台工具完成远端操作，并向用户返回结论。
  • 高危确认、步数/超时、凭证与沙箱全程生效；容量不足时摘要或切片。

总览

用户
  → Host / Harness（组装 Context）
  ↔ Model（推理 / tool_calls）
       ↓
  本地 Tools 或 MCP Client → Initialize → List → Call → Server → 外部系统
       ↓
  结果写入 Context → 再次请求 Model → … → 完成或强制终止

Prompt Engineering：指令、示例、结构化输出、工具调用意图（生成侧）
Context Engineering：整窗信息的选择、排序、压缩与检索
SKILL：流程规范注入 Context
MCP：Tools / Resources / Prompts
安全：Harness 与凭证硬约束；Prompt 为辅助
