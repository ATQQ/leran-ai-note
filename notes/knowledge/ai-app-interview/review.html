13 章 PE + Agent Stack notes/knowledge
01
AI 应用分层

Model 推理；Tools 声明并实现能力；Harness 编排运行时；Context 为送入模型的整包输入；Agent 为面向目标的多步自主循环。

层级职责
Model基于 Context 推理；生成文本或结构化 tool_calls
Context当前请求中实际送入模型的全部输入集合（构成见第 02 章）
Tools工具声明（schema）与可执行实现（本地脚本、API、MCP 等）
Harness运行时：消息循环、工具执行、结果回写、权限与资源控制、Context 组装
Agent在 Harness 之上、面向目标的多步自主循环，直至完成或被强制终止
1.1 Tools 的两面
面内容谁消费
声明（schema）名称、描述、参数类型与约束进入 Context，供 Model 决策
实现（implementation）真正执行的函数/脚本/远程调用由 Harness（或 MCP Server）调用，不把实现源码塞进 Context
1.2 Harness 与 Agent 的区分
HarnessAgent
性质运行时/编排引擎产品行为模式（如何用运行时追求目标）
典型职责组窗、调工具、回写、权限、步数与配额多步循环直至目标完成
关系Agent 运行在 Harness 之上无 Harness 则无法可靠完成工具循环
  • 模型不直接执行外部副作用；执行由 Harness 调度 Tools 完成。
  • 「带工具的单轮对话」具备 Tools，但缺少目标驱动的多步循环时，一般不称为完整 Agent。
02
Context Engineering

决定向模型窗口放入哪些信息、以何种顺序与篇幅放入，并使组合适配当前任务。Context 不是「用户那一句话」，而是 Harness 组装后交给模型的整包输入。

2.1 Context 的构成
构成项说明常见形态
系统层指令角色、全局规则、产品行为边界system 消息；项目级 rules
流程规范任务向 SOP（按需加载）已激活的 SKILL 全文或部分章节
工具声明模型可知的可调用能力与参数约束tools / MCP Tools 的 schema 列表
资源与提示模板可读参考、可套用提问包装（若接入）MCP Resources 内容；MCP Prompts 展开后的消息
当前用户输入本轮意图与约束user 消息；附件说明
对话历史此前 user / assistant / tool 轮次全文历史，或经摘要压缩后的历史
工具执行结果上一轮或本轮循环中外部调用的返回tool 消息；stdout、API JSON、错误信息（宜脱敏）
工作集材料与当前任务直接相关的代码/文档片段打开文件的切片、选区、诊断日志片段
检索材料从更大语料中按需取回的证据RAG top-k 片段；长期 Memory 命中条目
多模态附件若产品支持图片、截图等（计入窗口预算）
2.2 通常不进入 Context
内容原因
模型权重中的参数知识属于模型内部，不是本次请求的 Context
工具的真实实现代码 / 私钥 / Token留在 Harness 或 Server 调用路径；仅 schema 与执行结果（必要时脱敏）进入窗口
未加载的 SKILL 全文仅目录元数据在窗内；全文按需注入
未检索命中的仓库/记忆全量外置存储，禁止整库灌入
2.3 消息角色视角
system（含全局指令；可含已注入的 SKILL）
+ tools schema（并行通道或等价声明）
+ 历史消息序列（user / assistant / tool …）
+ 本轮 user
→ 送入 Model
2.4 与 Prompt Engineering 的关系
Prompt EngineeringContext Engineering
关注点指令如何编写（角色、任务、约束、格式、示例等）窗口内装载哪些内容、容量如何分配、如何压缩与检索
关系PE 产出的指令文本是 Context 的组成部分CE 统筹整窗信息，含 PE 文本、工具 schema、历史、检索结果等
2.5 优先级原则
  • 随任务动态调整，非固定表。参考顺序：当前用户请求 → 系统说明/已激活的流程规范（如 SKILL 全文）→ 工具 schema（任务需要工具时）→ 当前步骤的关键证据（工具结果、工作集文件片段、检索命中）→ 对话历史（可摘要）→ 大文件全文（应切片或摘要，避免整篇灌入）。
  • 工作集优先：与当前修改目标直接相关的文件片段、刚返回的工具结果，其优先级可高于无关历史与部分检索结果。
03
Context 组装策略

在窗口容量受限时，通过下列策略管理预算。策略可组合使用。

策略定义适用条件典型步骤
工作集切片（Chunk）从已确定对象中选取相关片段目标文件/对象已知定位对象 → 按光标/符号/相关性切段 → 写入 Context
摘要压缩（Summarize）将历史或长文压缩后写回后续 Context窗口不足，需保留要点选取旧轮次/长文 → 生成摘要 → 用摘要替换原文占位
RAG经索引/相似度检索后写入 top-k语料大、命中位置事先未知建索引 → 用当前问题查询 → 取 top-k → 写入 Context
长期 Memory窗外持久化，按需检索注入跨会话偏好、约定等写入外存 → 新会话按问题检索 → 仅注入相关条目
3.1 易混淆对照
对比差异
Chunk vs RAGChunk：对象已明确，做切片选择；RAG：对象未定，先检索再装载
压缩用摘要 vs 产品「总结」前者服务于 Context 预算；后者是给用户看的交付物
本轮历史 vs 长期 Memory历史在会话 Context 内（可摘要）；Memory 在窗外，按需注入，禁止每轮全量灌入
3.2 Memory 存储内容（示例）
  • 用户偏好、项目约定、跨会话事实、既往决策摘要等。
  • 注入规则与 RAG 类似：按当前任务相关性筛选。
04
Prompt Engineering 与 Function Calling

设计模型侧指令、示例与输出约束，以及工具调用意图的生成方式；执行仍由应用侧完成。

4.1 消息角色
角色含义
system系统约束与角色设定
user用户输入
assistant模型输出（可含文本与/或 tool_calls）
tool工具执行结果回传（通常携带 tool_call_id 与内容）
  • 多轮对话中，上述角色按时间序排列，构成模型可见的交互状态。
4.2 System Prompt 设计要素
要素说明
角色（Person）模型扮演的身份与能力边界
任务（Task）需要完成的目标
约束（Constraints）禁止项、安全与业务规则
输出格式（Output）期望的结构与呈现形式
  • 抽象规则的遵循能力弱于对具体示例的模仿；关键格式约束应辅以示例或 API 级约束。
4.3 Zero-shot 与 Few-shot
方式定义用途
Zero-shot不提供示例，直接下达任务任务模式常见、规则清晰时
Few-shot先提供输入→输出示例，再处理新输入需固定模式或覆盖边界情形时
  • 示例应覆盖边界情况；仅依赖系统提示中的抽象格式说明，字段级一致性仍可能漂移。
4.4 Chain of Thought（CoT）
  • 原理：自回归逐 token 生成；若不要求写出中间步骤，易发生跳步并提高错误率。强制展开中间推理可降低跳步风险。
类型做法适用
Zero-shot CoT使用引导语要求分步思考通用推理（数学、逻辑、常识）
Few-shot CoT示例中展示完整推理链领域特定推理方式需示范时
4.5 结构化输出
  • 可靠性由弱到强：仅在 System Prompt 中描述格式 → Few-shot 示范目标格式 → API 层 response_format / constrained decoding（在采样层面约束输出）。
  • 需要严格 schema 时，应优先采用 API 级约束，而非仅依赖提示词约定。
4.6 Prompt 调试
  • 流程：定位失败样例 → 最小改动修改提示或示例 → 回归测试（含未改动的相关用例，避免过拟合单点修复）。
4.7 Function Calling

本质：模型输出结构化 tool_calls；由应用侧代码执行工具，并将结果以 tool 消息写回后再次请求模型。

字段含义
id本次调用标识，用于与后续 tool 消息关联
name工具名称（须与 schema 中声明一致）
arguments参数对象（须满足 schema 约束）
  • Tool Schema 设计应包含：能力说明、适用场景、限制与参数约束（类型、必填、枚举等）。
单轮消息序（示意）
1) 请求 Model：messages + tools schema
2) Model 返回：assistant（含 tool_calls）
3) Harness 执行工具
4) 追加 tool 消息（content = 结果，绑定 tool_call_id）
5) 再次请求 Model
6) Model 返回：最终 assistant 文本（或继续 tool_calls）
流程说明
单轮通常涉及两次模型请求（决策调用 + 基于结果作答）
多轮无依赖可并行调用；有依赖须串行；需 max_iterations 与重复调用检测
错误处理一般失败可脱敏后回传模型；安全相关错误由代码层兜底
  • 职责划分：意图与工具选择倾向由模型完成；业务状态机、权限与安全校验由代码完成。
05
Harness Engineering

包裹模型的运行时层，负责使 Agent 循环可运行、可终止、可审计，并落实安全与资源策略。

5.1 职责子系统
子系统具体工作
循环控制维护「请求模型 → 若有 tool_calls 则执行 → 回写 → 再请求」；最大步数、超时、取消
工具编排解析 tool_calls、参数校验、路由到本地实现或 MCP Client、超时/重试
Context 管理组装第 02 章所列构成项；触发摘要/切片/检索
Memory 管线读写外置记忆；按需检索注入
权限与沙箱高危确认、文件系统/网络范围、工具白名单
资源治理token / 费用 / 并发上限
可观测性日志、trace、审计
5.2 与 Prompt 的边界
应由 Harness 强制可由 Prompt 表达
循环与步数上限；工具执行/超时/重试；高危确认；配额；Context/Memory 管线；日志语言、语气、详尽程度等偏好
  • 会造成不可逆损害、资源失控或循环无法收敛的行为，必须由代码强制；不得仅依赖提示词约束。
06
Agent Loop

标准阶段：感知 → 规划 → 行动 → 观察，可迭代执行。

阶段职责归属产出
感知模型判断信息缺口；Harness 调度 Tools 采集；结果写入 Context 后由模型再解释对问题的可操作理解
规划模型拆解步骤（定位、修改、验证）步骤列表或下一步意图
行动模型发出 tool_calls；Harness 调度；Tools 产生外部副作用外部世界状态变化
观察Harness 将执行结果写回 Context；模型评估是否达成目标继续循环或最终回复
6.1 嵌套关系
  • 感知阶段常已包含一次小型「行动→观察」（例如先读日志再下结论）。整体上仍是同一套 tool_calls 协议，而非另一套通道。
6.2 终止条件
类型触发方示例
正常完成Model判定目标达成，输出最终答复
强制终止Harness最大步数、超时、用户取消、配额耗尽
07
工具调用协议位置

执行依据为结构化 tool_calls，而非自然语言思考过程。

模型输出 assistant.tool_calls[]
  → Harness 校验 name/arguments（对照 schema）
  → 调度对应 Tool 实现（本地或 MCP）
  → 将结果写入 tool 消息（绑定 id）
  → 再次请求模型
规则说明
有 tool_calls才允许执行外部操作
仅有思考/闲聊文本不得据此执行命令或写文件
结果回写必须进入 Context，模型才能基于证据继续推理
  • 与 Function Calling（第 04.7 节）为同一机制在 Harness 中的落点说明。
08
SKILL

面向特定任务的流程规范（SOP），以文档形式存在，经 Harness 发现并注入 Context，供模型遵循。

8.1 常见文件构成
部分内容
元数据名称、描述（何时触发）、可选权限/依赖说明（如 frontmatter）
正文流程步骤、约束、输出要求、决策规则
附件可选 references/、脚本、模板等，按需再加载
8.2 进入 Context 的两级
级别进入窗口的内容时机
目录级name + description（技能清单）通常常驻或早期可见
全文级SKILL 正文及必要附件判定与当前任务相关之后
8.3 生命周期
  • 发现：扫描技能目录，暴露清单
  • 判定：用户显式指定 / Harness 匹配 / 模型依据描述选择
  • 加载注入：读全文 → 写入 Context
  • 遵循执行：模型按规范调用普通 Tools 或继续推理
  • SKILL 本身通常不是可 call_skill 的业务工具；外部副作用仍走 Tools / MCP。
09
MCP 能力模型

Model Context Protocol：Host 与外部能力进程之间的协议层。

9.1 三角色
角色定义
Host承载应用（如 Cursor）；内含 Harness 与一个或多个 MCP Client
ClientHost 内协议组件，与某一个 Server 会话
Server独立进程/服务，暴露 Tools / Resources / Prompts，并对接真实外部系统
用户 → Host（含 MCP Client）↔ Model
              ↓
         MCP Server → 外部系统（如 GitHub API）
  • 模型不与 Server 直连。
9.2 三类能力对照
能力是什么不是什么进入模型侧的方式
Tools可调用动作 + 参数 schema；Server 执行单纯文档说明schema 入 Context；调用经 tool_calls → Client → Server
Resources可读取的数据/文档Tools 的详细说明书读取后作为文本/资源内容进入 Context
Prompts可参数化的提示模板SKILL 目录 description；也非长篇渐进 SOP展开为消息后进入 Context
10
MCP 传输与生命周期
10.1 传输方式
传输特征适用
stdioHost 拉起本地子进程；stdin/stdout 交换 JSON-RPC本机集成（如 node server.mjs）
Streamable HTTP 等Server 独立监听网络端口远程/多客户端共享
  • stdio 约束：stdout 专用于协议报文；诊断日志写入 stderr。
10.2 生命周期步骤
Spawn → Initialize → List → Call（可多次）→ （进程由 Host 管理结束）
步骤说明之后模型侧可见变化
SpawnHost 启动 Server 并建立 Client通道就绪
Initialize握手：协议版本、双方能力声明会话参数约定完成
Listtools/list 等，枚举能力schema/清单进入 Context
CallClient tools/call；Server 执行结果作为 tool 消息回写 Context
  • 报文层通常为 JSON-RPC 2.0（请求含 method / params / id）。
  • 参考实现：notes/mcp-demo/。
11
SKILL 与 MCP 的调用关系
SKILLMCP Tool
进入路径规范文本注入 Contextschema 入窗后，经 tool_calls 由 Client 调用 Server
作用规定如何完成任务的流程与准则提供接触外部系统的可执行能力
组合可先注入 SKILL，再在其指导下调用 MCP 或其他 Tools
11.1 选择准则
条件倾向
需要统一流程、检查清单、教学/规范步骤SKILL
需要读写外部系统、远端 API、专用数据源MCP Tool（或其它 Tools）
既要规范又要远端操作两者：先 SKILL，后 MCP
  • 示例：显式指定流程技能 → SKILL；明确操作 GitHub → MCP；按规范审 PR 并留评论 → SKILL + MCP。
12
权限、沙箱与安全边界
12.1 控制分层
层手段强度
Prompt文字禁止与行为偏好软约束，可被模型忽略
Harness拦截、确认、白名单、沙箱、脱敏、步数/配额硬约束
凭证与 ServerToken scope、服务端鉴权硬约束
外部环境OS 权限、网络策略硬约束
12.2 风险与控制面
风险类型主要控制面
高危本地操作（如破坏性删除）Harness：拦截、二次确认、沙箱
外部凭证权限过大凭证最小权限；Server/平台侧 scope；Host 可对敏感操作再审批
密钥或敏感文件外泄Harness：禁读、脱敏、拦截外发；凭证仅在调用路径使用，不写入模型 Context
任务所需能力过宽工具白名单、网络/文件系统沙箱，按任务授予最小能力集
  • Prompt 中的安全说明不能替代代码与凭证层硬约束。
13
端到端结构（编码助手示例）

任务形态：定位缺陷 → 修改代码 → 验证 → 创建 Pull Request。

步骤主要层级工作内容
1 组窗Harness / CE系统说明、项目约束、工具与 MCP schema、SKILL 目录或全文、代码/日志工作集
2 循环Model + Harness + Tools规划 → tool_calls → 执行回写 → 观察；直至完成或强制终止
3 远端变更MCP / Tools创建 PR 等
4 回复用户Model结论与说明
5 全程闸门Harness / 凭证高危确认、步数/超时、沙箱与最小权限
6 容量管理CE摘要、切片、按需检索

总览

用户
  → Host / Harness（组装 Context：系统 · SKILL · schema · 历史 · 工作集 · 检索 · tool 结果…）
  ↔ Model（推理 / tool_calls）
       ↓
  本地 Tools 或 MCP Client → Initialize → List → Call → Server → 外部系统
       ↓
  结果写入 Context → 再次请求 Model → … → 完成或强制终止

Prompt Engineering：指令、示例、结构化输出、工具调用意图（生成侧）
Context Engineering：整窗构成、排序、压缩与检索
SKILL：元数据常驻 + 全文按需注入
MCP：Host/Client/Server；Tools / Resources / Prompts
安全：Prompt 软约束；Harness 与凭证硬约束
